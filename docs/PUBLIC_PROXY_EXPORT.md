# Public proxy export site

`proxy.secpath.space` is a static GitHub Pages site generated by GitHub Actions. It is intentionally separate from the Flask dashboard and does not expose a ProxyPool API, database, runtime process, or JSON list of proxy endpoints.

## Public surface

The page contains three downloads only:

- Top 20 SOCKS5 proxies
- Top 20 SOCKS4 proxies
- Top 20 HTTP/HTTPS proxies

The endpoint list exists only inside the generated Excel workbooks. `index.html` and `metadata.json` contain aggregate counts, timestamps, workbook checksums, and download paths—not proxy IPs, ports, source URLs, credentials, or raw validation errors.

## Pipeline

The workflow in `.github/workflows/public-proxy-monitor.yml` runs manually or every two hours:

1. Fetch HTTPS source files from `public_monitor/sources.ini`.
2. Normalize and deduplicate public IP endpoints.
3. Prefer candidates corroborated by multiple sources and rotate the remaining sample.
4. Validate candidates repeatedly through HTTPS destinations.
5. Rank successful candidates by reliability, latency, jitter, exit-IP consistency, source corroboration, and remote DNS support.
6. Export up to 20 results per protocol family as XLSX.
7. Build a static marketing page and deploy it through GitHub Pages.

No workflow step calls the deployed ProxyPool dashboard.

## GitHub setup

1. Push the repository to GitHub.
2. Open **Settings → Pages**.
3. Select **GitHub Actions** as the publishing source.
4. Open **Actions → Validate and publish public proxy exports**.
5. Run the workflow manually once.
6. Confirm that the `github-pages` environment deploys successfully.

The workflow uses the current Node 24-compatible major releases of the official Pages actions:

- `actions/checkout@v7`
- `actions/setup-python@v6`
- `actions/upload-pages-artifact@v5`
- `actions/deploy-pages@v5`

## Custom domain

The generated artifact contains:

```text
CNAME
```

with this value:

```text
proxy.secpath.space
```

Create a DNS CNAME record for `proxy.secpath.space` pointing to the GitHub Pages hostname for the repository owner, then confirm the custom domain in GitHub Pages settings and enable **Enforce HTTPS** after certificate issuance.

Do not point the root domain through a wildcard record. Keep any operational dashboard or API on a different hostname.

## Local build

Create and activate a virtual environment, then install the monitor-only dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r public_monitor/requirements.txt
```

Build a smaller local sample:

```bash
python3 -m public_monitor.run \
  --sources public_monitor/sources.ini \
  --output public_site \
  --max-candidates 80 \
  --workers 32 \
  --timeout 4 \
  --probes 1
```

Serve the generated directory:

```bash
python3 -m http.server 8080 --directory public_site
```

Open `http://127.0.0.1:8080`.

## Tuning

The production workflow defaults are conservative enough for GitHub-hosted runners:

```text
700 candidates per protocol family
96 worker threads
5-second proxy timeout
2 probes per candidate
20 exported results
45-minute workflow timeout
```

Increasing the candidate cap, probe count, or timeout can improve coverage but also increases runner time and load on public infrastructure.

## Workbook fields

Each workbook contains:

- Rank
- Protocol
- IP
- Port
- Proxy URL
- Exit IP
- Success rate
- Median latency
- Jitter
- Remote DNS support
- Verified curl scheme
- Checked time
- Composite score

A second worksheet explains responsible use and links back to the ProxyPool repository.

## Security and responsible use

- Only unauthenticated endpoints from committed public source lists are accepted.
- Source URLs must use HTTPS.
- Private, loopback, link-local, reserved, and otherwise non-global IP addresses are discarded.
- Source bodies are capped at 2 MB.
- Raw sources and raw validation errors are not copied into the Pages artifact.
- Public proxies must be treated as hostile and ephemeral.
- Never use these exports for passwords, personal data, session cookies, private administration, financial activity, or other sensitive traffic.
- A successful check proves only that a GitHub runner reached a target through that proxy at that moment.
